# AI-Moderated Discussion Forum — Plan v5

Earlier versions are in `docs/plan_v1.md` … `docs/plan_v4.md`. v5 adds a server-enforced message length limit and turns the build order into step-by-step build instructions (section 14).

## 0. How to use this plan
- Build **one step of section 14 at a time**, in order. Each step lists what to build, the tests to write **first**, and when it counts as done. Don't start a step until the previous one is done and its tests pass.
- Sections 1–13 are the reference design that the steps point back to. If building a step shows the design is wrong, update this file first, then the code.
- **No real API call happens before step 3,** and only after the Anthropic Console spend limit (3.1) is set and the budget guard (step 2) is finished.
- Every number you might want to change lives in `config/tunables.py`.
- **Working method (from step 2 on):** a **coding agent** writes the implementation and a **separate testing agent** writes and runs the tests for each component, so the tests aren't written by the same agent that writes the code. Claude (the main agent) owns the **system architecture**: it hands each agent a precise brief drawn from this plan, reviews what comes back against the design, and integrates it. The user approves each step before the next begins.

## 1. Goals and constraints
- Build a minimal two-person discussion board where an AI moderator makes the discussion more productive **while staying politically neutral**.
- **Neutrality:** given two equal contributions (equal factual support, clarity, logic, procedural conduct), the system intervenes at equal frequency, in an equal manner, with equal intended effect. This holds regardless of political position (first priority), and later regardless of speaker identity, speaking order and content features such as length.
- **Log first.** The website is step one. A separate bias-evaluation pipeline uses its logs. Every moderation decision, including "no intervention", is logged in a structured form that can be reconstructed and fetched in batches.
- **Two stages, measured separately, for every issue dimension:**
  - **Detection:** does the Master Moderator notice a problem?
  - **Action:** given a noticed problem, does the Intervenor act on it?
- **Cost must stay VERY modest.** The user pays for the API calls.

## 2. Decisions (agreed)
- **Stack:** Python 3.13 + Django 6.1, SQLite (WAL mode), server-rendered pages, small JS polling every ~3s. Python 3.13 works on every host checked, including PythonAnywhere, which has no 3.14.
- **Accounts:** username + password, **no email** (owner decision 2026-09-26, step 6c), using Django's own auth (section 10).
- **LLM:** Claude only, through the Anthropic SDK. Only `moderation/llm.py` may import `anthropic`, and a test enforces this.
- **One settings file for everything you would tune:** `config/tunables.py` holds the dollar caps, input and traffic limits, the kill switch, model choices and analysis thresholds, each with a comment. Secrets (API key, email credentials, Django secret key) live in `.env`, never in code.
- **Trigger:** the Master Moderator → Intervenor pipeline runs after every user message. At most one moderator post per user message. **The moderator never replies to its own messages** (a moderator message never triggers a run, and it is never itself moderated). This is enforced in four independent layers, so a bug in one cannot start a reply loop:
  1. **Creation:** `post_message()` (the only path for user messages) enqueues a run; the function that posts a moderator message (used only by the pipeline) never enqueues one. They are separate code paths.
  2. **Data:** a `ModerationRun` cannot be created (or saved) unless its `trigger_message` has `author_type = "user"`: checked in the model's validation and by a database trigger (SQLite `BEFORE INSERT/UPDATE` trigger created in a migration), so even raw SQL or the admin cannot create one. Replays follow the same rule.
  3. **Pipeline:** `run_moderation(run)` re-checks the trigger before any LLM call; a run whose trigger is not a user message is marked `failed` with reason `invalid_trigger`, makes no call, writes no ledger row and posts nothing. Issues the Master reports on a moderator message are rejected at item level (they never reach the Intervenor). A live run posts at most one moderator message, enforced by the one-to-one `posted_message` link.
  3b. **Prompts:** the Master prompt says moderator messages are read for context only and never reported on (already the case).
  4. **Cost backstop:** even if all of the above failed, the budget guard, the 30-second gap and the per-conversation caps bound the damage.
- **Message length:** user messages are capped at `MAX_MESSAGE_CHARS` (default **3,000 characters**, about 500 words), enforced on the server and explained to users (section 4).
- **No talk of costs to users (owner decision, 2026-09-26).** Pages and messages never mention API costs, spending or budgets. Limits are explained by keeping the discussion readable; when moderation is paused the page says only that it is paused and that messages are still posted. The composer has no helper paragraph under the Post button.
- **Conversations are between two positions (owner decision 2026-09-26, revised).** Every proposition has two positions. A seeded proposition carries both wordings ("My position is that X" and "My position is that not X"); a user-created proposition carries the proposer's own wording (the form starts "My position is that ...") and its other side is the plain choice "I disagree with this position". A person chooses a side; each participant records a side (`pro` = the stated position, `con` = the opposing one) and the two participants of a conversation always hold opposite sides. Choosing a side joins the oldest waiting conversation whose waiting person holds the opposite side; otherwise a new conversation starts and waits for someone on the other side. Two people waiting on the same side do not pair with each other. The AI moderator and the raters see only the neutral claim (the stored proposition), never which participant holds which side. New columns: `Topic.opposing_position` (optional text) and `Participant.side` (forum migration 0003). Brief: `docs/step7c_brief.md`.
- **The home page lists only what is waiting (owner decisions 2026-09-26).** It shows the positions that someone holds and is waiting for someone to disagree with (one card per topic and side, never the viewer's own), each with one button that takes the other side, and a "Start a new discussion" button. The viewer's own conversations are on a **separate page, "Your discussions"** (open, active and ended, with a search box "Search your discussions"), reachable from a link in the site header, so an active conversation is never lost. Everything else is started from the propose page: write your own position, or start from one of the seeded topics (both sides offered). The seeded topics may be dropped later; until then they appear only on the propose page. Brief: `docs/step7c_brief.md`, Revisions 3 and 4.
- **Usernames are shown, and people can block each other (owner decisions 2026-09-26).** The two participants of a conversation see each other's usernames (in the conversation page, the speaker labels and the moderator notes' headings), and the home page's waiting cards show the waiting person's username, so people can avoid particular participants. A new table `forum.Block` (blocker, blocked, created; forum migration 0004) makes a block work in both directions: neither person sees the other's waiting positions on the home page, and pairing never puts them together. Blocking someone ends every conversation the two share, exactly like the End button (read-only for both). A silent block: the blocked person is not told. Block controls: in the conversation page, on each waiting card, and a "Blocked people" page (linked from "Your discussions") to review and unblock. The AI moderator, the raters and the prompts still never see usernames, labels or sides; exports still show usernames only with `--include-identities`. This reverses the earlier rule that participants never see each other's names. Brief: `docs/step7c_brief.md`, Revision 5.
- **A waiting conversation is usable (owner decision 2026-09-26).** The first participant can post while waiting for the second, with **no separate limit** beyond the normal 30-message and 30-second rules. The AI moderator reviews those messages exactly as it reviews any other. When someone joins, they see everything already posted. The home page does NOT preview the opening message (owner decision, same day); the earlier rule "you can post once someone else joins" is gone.
- **User-created propositions (owner decisions, 2026-09-25).** Any logged-in user can create a proposition to debate; it appears on the home page **immediately** (no review, no AI screening, so no added cost or new bias channel), listed **newest first with a search box**, and shown as the proposition text only (no separate topic title, no thread lists or counts). Guards: `MAX_PROPOSITION_CHARS` (default 200), `MAX_PROPOSITIONS_PER_USER_PER_DAY` (default 20, UTC), both in `config/tunables.py`, enforced on the server with the same explain-why rule as messages; an admin can hide a proposition (`hidden` flag; existing conversations are kept). Creators do not take a side and are not asked to. Seeded propositions (with `leans`) remain the basis of the paired political-direction tests; user-created ones have no `leans`, so their conversations are observational data only until someone labels them (section 18).
- **Labels are never shown to users (owner decision, 2026-09-25).** The A/B labels stay internal (random assignment, seed stored, logged, given to the moderator). Users see only "You" and "The other participant". Consequences: moderator posts must not name participants by label in their text; the page adds a per-viewer heading computed from the act's `addressee`/`subject` ("About your message 4", "About the other participant's message 3", "For both of you"); the Intervenor's style rule changes accordingly (needs the owner's OK before step 3 is frozen).
- **Who can read a conversation:** only its two participants (the same membership check that gates posting); researchers see everything through admin and exports. There is no public preview of a waiting conversation (owner decision 2026-09-26: the home page shows positions only, not opening messages).
- **Site name: "Think Together" (owner decision 2026-09-27).** Replaces "AI-Moderated Discussion Forum" everywhere a user can see it (browser title, site header/brand link, error pages, README, this plan). Internal names (repo, package names, `docs/` filenames) are unaffected.
- **Owner feedback wave, first playtest (owner decisions 2026-09-27, brief `docs/wave16_brief.md`):**
  - **Navigation:** the header shows two equally prominent links, "Waiting to discuss" (the home page) and "Your discussions", instead of the current single plain "Your discussions" link with the site brand as the only way home.
  - **Blocking is conversation-only.** The block control on each home-page waiting card is removed; blocking is only offered from inside a conversation (the disclosure already there). The reason: blocking from a waiting card, with only a username and no conversation, was judged too easy to do by mistake or on a whim.
  - **Moderator messages get their real sequence number** shown, exactly like user messages ("message 4"), instead of the unlabelled "automated" they show today. `seq_no` was always a single shared sequence for the conversation (user and moderator messages together); only the display hid the moderator's numbers, which made the visible numbering of user messages look like it skipped some.
  - **Multiple intervention acts in one moderator message get a visible break between them** (the acts are joined with a blank line in the stored text, but the template renders it as a single collapsed space, so two acts can read as one run-on sentence). Fixed by rendering each act as its own paragraph.
  - **Master/Intervenor prompt precision (found from a real transcript, step 3.1 cleanup, no schema change):** the Master must distinguish a participant *asserting* a factual claim from a participant *denying, negating, or noting the absence of evidence for* the same claim (e.g. "you haven't shown that X" is not an assertion of X, and must not be reported as `unsupported_claim` attributed to the speaker as if they were the one claiming X). The swap test in `master_v1.md` already requires this kind of care; the prompt is amended to say so explicitly with a worked example. `request_information` acts are phrased as a question ("Could a source be given for...?"), never a flat assertion ("A source... would help..."), matching the type's own definition ("asks and does not decide").
  - **Removed explanatory sentences on the How this works page** that were judged unnecessary detail rather than deleted design decisions: how the moderator is told about sides, the username/blocking mechanics (both already covered by the page's own controls), that the moderator replies once per message and never to itself, and that it is instructed to be neutral (the neutrality guarantee itself is unchanged; only the sentence describing it in this location is removed). "Tell the site admin" (no contact channel exists) and the bracketed retention-period placeholder are also removed; the two were the only bracketed placeholder text anywhere in the user-facing inventory (`docs/user_facing_text.md`), so none remain.
  - **Unlimited discussions per proposition (owner decision, 2026-09-27).** `enter_proposition`'s pairing rule 1 ("return the user's own existing open/active conversation on this topic") is removed: choosing a side always tries to pair or create, exactly as if the user had no history with that proposition, so a user may hold as many separate discussions on the same proposition as they want. Nothing is added to shortcut this — no "start another" button — starting a second discussion means going through the propose page again, same as the first time. The propose page's "Open your conversation" button is unaffected: it remains a separate way to jump back into an existing conversation, not folded into the side-choice buttons. Not yet scheduled as a build step; needs a brief.

- **Factual research via web search (owner decision, 2026-09-27; scope finalized 2026-09-27 after a design conversation about how it interacts with the existing pipeline).** The owner's view: the moderator's most valuable function is supplying factual background, not tone-policing, and participants are expected to debate current events, so knowledge frozen at the model's training cutoff is a real, expected failure mode. **Governing principle, settled after the initial Step 20a build:** the existing pipeline — the Master's own confident issue-detection and the Intervenor's `correct_factual_error`/`provide_information` acts, asserted directly from parametric knowledge, exactly as built since step 5 — is UNCHANGED and continues to handle every clear-cut case, evaluated exactly as today (section 9's existing matched-pair/golden-transcript framework, no change). The web-search offer is a **fallback for the cases that pipeline can't confidently handle**, not a replacement for it, and it is evaluated **separately** (see below), not folded into the existing detection/action metrics. Rejected explicitly: routing *all* factual content through search-and-click, including obvious cases the model can already correct outright — that would weaken the moderator exactly where directness is cheapest and safest, and would entangle the existing, working evaluation methodology with the harder-to-measure click/uptake dynamic for content that never needed it.
  - **The Master's new field is broader than "might be outdated" — renamed accordingly.** Originally built (step 20a, committed) as `time_sensitive: bool`, scoped only to recency. Corrected 2026-09-27: recency is only one reason the existing pipeline can be inadequate for a checkable claim; a second, independent reason is that the model might be wrong or fabricating a specific detail (a citation, a statistic, a study) regardless of when it happened — the taxonomy's own worst-case rubric example ("a 2024 Harvard study proved the Moon is hollow") is fabrication, not staleness. The field is being renamed and broadened (exact name TBD in the revision brief, e.g. `needs_verification`) to mean: this checkable claim is one the Master can't confidently let the existing pipeline assert on directly, for either reason. The *reason* is never surfaced to users (only that a check can be requested), so the field stays a plain, undifferentiated boolean — no reason sub-field, matching the original design's simplicity.
  - **The Intervenor's new act type** (`offer_research`, already built) is chosen only in response to a flagged issue, and only when the existing act types aren't the better fit for it — it does not search anything itself, it posts a moderator note plus a "Provide factual background" control, visible to both participants like any moderator message; either may click it, and the first click claims the run (no duplicate research on one issue).
  - **One new component, not two:** clicking the control queues a new `ModerationRun` kind (alongside `live`/`replay`, e.g. `research`) that the existing worker processes through a single new step — a `web_search`-tool-enabled call that produces a short, sourced, neutral note, posted as an ordinary moderator message when ready. This reuses the existing async run/worker/poll machinery; no new async plumbing. Explicitly rejected: a separate LLM stage just to *identify* research-worthy claims (the Master's flag already does that), a standing always-available "get research" button not tied to a specific moderator-flagged claim, and a free-text box letting a user type what they want researched (raised and rejected 2026-09-27: it would let a user's own leading framing get laundered through what reads as independent research, and breaks the moderator-decision measurability the rest of this feature depends on) — see section 18's post-MVP list.
  - **Confirmed technical facts from a real, guarded spike (2026-09-27, ~$0.11 spent, under the $0.50 approved):** structured output composes with `tools` in one `messages.parse()` call — no second call needed; everything comes back in one response (`stop_reason=end_turn`), no client-side search loop; the billable signal is `usage.server_tool_use.web_search_requests` (a count, not a dollar figure — `pricing.py` needs its own per-search rate); real latency ranged 15s (1 search) to 157s (4 searches); `max_uses` is a hard ceiling the model visibly bumps against; `max_tokens` needs real headroom once several searches' results are in context.
  - **Button eligibility widened beyond `offer_research` (owner decision, 2026-09-27, in two passes):** the "Provide factual background" button is available on any valid act addressing a checkable factual claim — `offer_research`, `correct_factual_error`, `provide_information`, or (added the same day, after an owner report that a real "Could a source or study be given for..." message had no button) `request_information` — not only the ones the Master flagged `needs_verification`. `request_information` fits the rationale at least as well as the first three: it is the Intervenor explicitly saying it has no confident answer of its own. A confident, directly-asserted correction stays exactly as it is; a participant can still ask for an independent, search-backed second opinion on it anyway. Still not a free-text box and not a standing always-on control — it's attached to a specific moderator act either way. `request_clarification` (about vagueness, not a factual claim) and every other act type remain ineligible.
  - **Preview integration (owner decision, 2026-09-27; not yet built, scheduled after Step 20b's core lands and is verified):** the intervention preview (step 19) gains a third choice, "Post and request background," alongside "Edit" and "Post as written" — it posts the draft as written and immediately fires the research request on the resulting real act. Editing after seeing researched background, or researching a draft before deciding to post it, is explicitly not built; see section 18's post-MVP list for why and the accepted tradeoff.
  - Evaluation approach: section 9 (new test family, kept separate from the main detection/action metrics as above). Known, deliberately deferred risks: section 18, "For post-MVP design".
- **Neutrality inputs:**
  - Moderator LLMs see only `Participant A/B` labels: no usernames, emails, stance or lean.
  - A/B labels are assigned **at random when the conversation is created** (the creator gets one at random, the person who joins later gets the other). The seed is stored on the conversation at creation. Speaking order and join order are logged separately, so position bias stays testable.
  - Political labels are never collected from users.
- **Stance and position:** each message gets a `stance` label (pro/con/neutral) relative to the topic's proposition. Position is derived from `Topic.leans`, a JSON field, under several schemes (`compass` with economic and social axes, `us_partisan` with a party axis). Values run from −1 to +1. One headline scheme is chosen before the evaluation.
- **Issue dimensions and intensity:** problems are described by a *dimension* (e.g. `factual_accuracy`, `abusiveness`, `clarity`) and an *intensity* from 0 to 4, attached to a **phrase** of a message (or to the whole message when the whole message is the problem). Human and LLM raters use the same scheme and may mark a phrase "not scorable" with a reason.
- **Judge:** one Anthropic model (`JUDGE_MODEL_SEEDED`) tags the moderator's responses. (The earlier two-model panel was removed in cleanup 1; a human panel is future work.)
- **TDD:** pytest + pytest-django, tests first. `FakeLLM` for the plumbing. A **golden set** of transcripts checks prompts against the real API (small, on demand, budgeted).
- **Runner:** a separate worker process, not an in-process thread (section 11).

## 3. Cost controls
### 3.1 Anthropic side (the user sets these once in the Console, before step 3)
Checked against Anthropic's docs. These are separate from any claude.ai or Claude Code subscription.
1. Console (platform.claude.com) → **Settings → Workspaces → create a workspace** (e.g. `discussion-forum`). The **Default Workspace cannot have limits**, so the project must not use it.
2. In that workspace's **Spend limits** tab, set a monthly cap (**$10**). Create the API key **inside that workspace** and put it in `.env`.
3. Also set an **organization limit** under **Settings → Billing → Spend limits** as a second backstop.
4. When a limit is hit, requests fail with **HTTP 400, `invalid_request_error`**, message starting "You have reached your specified … usage limits". The org tier cap instead returns a 429 with `error_code: enforced_spend_limit_reached`.
5. **Caveat:** the docs don't promise cut-off to the cent or in real time, so this is the backstop. The app-side guard is the first line of defense.
6. Not verified: how prepaid credits and auto-reload interact with the limit. Check the Billing page yourself.

### 3.2 App side (built in step 2)
All enforced in the single `llm.call()` function. `manage.py budget` prints the current caps, the path of `config/tunables.py`, and the spend so far.
- **Price table** (`moderation/pricing.py`): per-model input, output, cache-write and cache-read prices, checked against Anthropic's pricing page when implemented. An unknown model means **no call** (fail closed).
- **Ledger:** every call stores `cost_usd`. Totals are sums over `LLMCall`, grouped by `purpose` (moderation / spike / golden / replay / judge), by day, and by conversation.
- **Reservation before each call:** the worst-case cost (counted input tokens × input price + `max_tokens` × output price) is added to the spend so far. If that would pass **any** applicable cap, the call is refused. A refused moderation run is marked `skipped_budget` and logged, so skipped runs show up in the data.
- **Bounded input:** because messages are capped (section 4) and only the last `TRANSCRIPT_MAX_MESSAGES` are sent, the worst-case cost of one run has a known upper bound. `manage.py budget` prints it.
- **Fail closed:** if the ledger can't be read, no call is made.
- **Circuit breaker:** trips on either spend-limit error, or on 5 consecutive API errors within 5 minutes. Once tripped, no calls until `manage.py reset_breaker`. The SDK's `max_retries` is 1.
- **Kill switch:** `LLM_ENABLED = False` turns LLM calls off, and runs are marked `skipped_disabled`. It is **off by default**: the user switches it on deliberately once the Console spend limit is set.
- **Prompt caching:** the system prompt, taxonomy, rubric and the earlier part of the transcript are sent as a cacheable prefix, with only the newest messages after the cache breakpoint. This is the biggest single cost lever, because every run re-sends a growing transcript. Cache tokens are recorded and priced separately.
- **Traffic limits:** `MIN_SECONDS_BETWEEN_MESSAGES` per participant, `MAX_USER_MESSAGES_PER_CONVERSATION`, `MAX_OPEN_CONVERSATIONS`, `max_tokens` per agent.
- A test fails if any tunable name is assigned anywhere except `config/tunables.py` (checked by parsing the source).

## 4. Input limits (server-enforced, explained to users)
**Message length.** `MAX_MESSAGE_CHARS` in `config/tunables.py`, default **3,000 characters** (about 500 words).
- **How characters are counted** (one function, `forum/limits.py: count_message_chars`, used everywhere): line endings are normalized to `\n`, the text is Unicode-normalized (NFC), leading and trailing whitespace is stripped, and the remaining Unicode characters (code points) are counted. An emoji counts as one character.
- **Enforced on the server.** Every path that creates a user message goes through one service function, `forum/services.py: post_message()`, which validates length (and emptiness and the rate limits) before anything is saved. Views never create `Message` rows directly. A request that skips the page (e.g. a hand-made POST) gets the same rejection. Over-limit messages are **not saved, not moderated and cost nothing**.
- **Explained to users:**
  - The compose box shows the limit and a live counter ("2,950 / 3,000"). The counter uses the same counting rule (code points, trimmed), so it agrees with the server. It is guidance only: the server decides.
  - The browser does **not** silently truncate text (no `maxlength` attribute), so nothing a user wrote is lost without them seeing it.
  - An over-limit post returns the form **with the user's text still in it** and a clear error, e.g.: *"Your message is 3,412 characters; the limit is 3,000. Please shorten it by 412 characters. Messages are capped to keep the discussion readable and to keep the AI moderator's running costs low."*
  - The same short explanation appears on the "How this works" page, alongside the rate limit.
- **Whenever a user cannot post, the page tells them why, in plain words, and what they can do next.** `post_message()` never fails silently and never with a generic error: it raises a `PostRejected` carrying a stable `code`, a user-facing `message`, and `retry_after` seconds where relevant. The view shows that message next to the compose box and keeps the user's text; for standing conditions it also disables the compose box and shows the reason. The server decides; any countdown on the page is guidance only. The reasons and their wording:
  - **Empty message:** "Your message is empty."
  - **Too long:** the message described above (count, limit, reason).
  - **Too fast** (`MIN_SECONDS_BETWEEN_MESSAGES`, **30 seconds**): "Please wait 12 more seconds before posting again. Messages are limited to one every 30 seconds to keep the discussion readable and the AI moderator's running costs low." The wait is measured from the same participant's previous message, on server time.
  - **No turn-taking rule (owner decision, 2026-09-25).** Nothing stops one participant posting several messages in a row, and nothing requires the other person to reply first: that is realistic, and how the moderator responds to it (flooding, unanswered questions) is something we want to observe. The only limits on posting are the 30-second gap (a rate limit, not a turn rule), the per-conversation message cap and the length limit. The database, the models and `post_message()` must not enforce alternation; the flooding series exists to test the moderator's response to it.
  - **Conversation full** (`MAX_USER_MESSAGES_PER_CONVERSATION`): "This conversation has reached its limit of 30 messages and is closed. You can start a new one."
  - **Conversation closed:** "This conversation is closed."
  - **Not a participant / thread full:** "You are not a participant in this conversation." and "This conversation already has two participants."
  - **Not logged in:** a redirect to the login page with a sentence saying what to do ("Please log in"). (The earlier "email not confirmed" case is gone with the email flow, step 6c.)
  - **Something failed on our side:** "Something went wrong on our side and your message was not sent. Your text is still in the box; please try again." (details go to the log, not the page).
  - **Moderation paused** does not stop posting; the page says so and why, in plain words ("The AI moderator has reached today's spending limit and will resume tomorrow", "...this conversation's limit", "moderation is switched off", or "the moderator ran into a problem"), and that messages are still posted. It never shows internal error text.
- **Synthetic messages** (paired test sets) are held to the same limit, so the test conditions match what real users can post.
- **Other text inputs:** username 3–30 characters, **ASCII letters, digits, `_` and `-` only** (so no two usernames can look alike on screen); email up to 254 characters. The username rule is enforced on the model, so every way of creating an account obeys it (forms, `create_user`, `createsuperuser`, admin, plain `save()`).

## 5. Taxonomy and dimensions (single source: `moderation/taxonomy.py`)
The database choices, the Pydantic schemas and the prompt text all come from this one file. Each type has a one-sentence definition, boundary rules and examples.

**Issue types (Master Moderator):** `unsupported_claim`, `possible_factual_error`, `unclear_statement`, `fallacy`, `strawman`, `abusive_language`, `repetition`, `process_violation`.
- `unsupported_claim` means a factual assertion with no support, which may be true. `possible_factual_error` means an assertion that is likely false.

**Dimensions:** an issue type may map to a *dimension* that has an intensity rubric. Adding a dimension means adding a rubric file and a registry entry, with no schema change.
| Dimension | Issue type | What it measures | What raters record |
|---|---|---|---|
| `factual_accuracy` | `possible_factual_error` | how wrong a factual claim is | every checkable claim, including accurate ones (intensity 0), so false-positive rates have a denominator |
| `abusiveness` | `abusive_language` | how abusive a phrase is | only phrases with intensity of 1 or more; a message with no such phrase counts as 0 |
| `clarity` | `unclear_statement` | how hard a statement is to understand and respond to (added step 21) | only phrases with intensity of 1 or more |

**Rubrics** are versioned files, `rubrics/<dimension>_v1.md`, used **verbatim** in the LLM prompts and in the human raters' guidelines. Draft anchors, to be finalized before the pilot:
- `factual_accuracy`: 0 accurate; 1 minor imprecision; 2 materially misleading or overstated; 3 clearly false; 4 flagrantly false or fabricated.
- `clarity` (step 21): 0 clear; 1 slightly vague; 2 ambiguous; 3 hard to respond to; 4 unintelligible. Scores the statement, never the speaker; register, dialect, formality and harmless typos are 0, and a clear statement the reader disagrees with is 0. For a clarity issue the Intervenor prefers `request_clarification` (a question) to `clarify_argument` (a restatement), and restates only when sure of the meaning.
- `abusiveness`: 0 none; 1 mildly rude, dismissive or sarcastic; 2 mocking or contemptuous toward the person; 3 direct insults or demeaning language; 4 slurs, dehumanizing language, threats or harassment.

**Not scorable is an outcome, not a score.** A rater may decline to give an intensity and must say why: `unverifiable` (no reliable evidence either way), `contested` (credible sources genuinely disagree, or the claim rests on a value judgment), or `needs_context`. Contested political claims must not be forced onto the 0–4 scale, because whoever does the forcing decides the "truth", and that is exactly where bias would enter the ground truth. How often each side's claims are called `contested` or `unverifiable` is reported by side.

**Act types (Intervenor):** `provide_information`, `correct_factual_error`, `improve_argumentation`, `clarify_argument`, `restate_positions`, `identify_agreement_disagreement`, `request_information`, `request_clarification`, `enforce_conduct`, `enforce_process`.
- `clarify_argument` restates without changing content. `improve_argumentation` flags a reasoning problem. `enforce_process` covers flooding, turn-taking, and prompting a party to respond.

**Decision:** `intervene` | `no_intervention`. **Tone (self-reported per act):** `gentle` | `neutral` | `firm`.

## 6. Agent inputs and outputs (Pydantic, validated)
**Master Moderator (detection)** input:
- the transcript up to `snapshot_seq` (at most the last `TRANSCRIPT_MAX_MESSAGES`), with `Participant A/B` labels and message ids
- earlier moderator posts
- issues already raised, with their outcomes, marked already-raised
- process facts computed in code (consecutive messages per participant, time gaps)

**Only-new-issues rule:** the Master flags issues in the *newest* message, plus inherently cross-message issues (`repetition`, `strawman`, `process_violation`). An issue on an older message with any other type is kept in the log, marked rejected, and neither counted nor passed to the Intervenor.

**Phrase-level issues:** each issue quotes **the specific phrase** that has the problem, or the whole message only when the whole message is the problem. The LLM returns only the quote text, never character offsets. Code finds the quote in the message: an exact match first, then a normalized match (whitespace, straight vs. curly quotes, case). It stores the offsets and the match type. For issue types with a dimension, the Master also gives an `intensity` (0–4) on that rubric.

Output:
- `issues[]`: `{id, message_id, issue_type, quote, explanation, confidence, intensity?}`
- `discussion_map`: `{agreements[], disagreements[{summary, kind: factual|normative}]}`

**Intervenor (action)** input: the transcript and the Master's valid issues. **Summary due (step 21, owner decision 2026-10-01, N = 4):** the pipeline computes `summary_is_due(run, discussion_map)`: true for a live run when the number of user messages up to the trigger is a positive multiple of `AGREEMENT_MAP_EVERY_N_USER_MESSAGES` (4; 0 or None turns it off) and the discussion map has at least one agreement or disagreement. Replay, research and preview runs are never due. When due, the Intervenor is called even with no valid issues and gets a `<summary_due>` block; it should include one `identify_agreement_disagreement` act built only from the map, in impersonal wording, equal weight per position, counted in the 3-act limit (leaving it out is not an error). A preview draft check never fires the note, and a due live run reuses a preview's Master output but calls the Intervenor afresh. The note is posted as an ordinary moderator message.

Output:
- `decision`, `rationale`
- `issue_dispositions[]`: for **every** valid issue, `{issue_id, disposition: acted|declined, reason}`
- `acts[]`: `{type, addressee (A|B|all), subject (A|B|both|none), source_issue_ids, source_message_ids, tone, text}`, at most `MAX_ACTS_PER_INTERVENTION` (default 3)

**Validation happens at two levels:**
- **Structural** (invalid JSON, or doesn't match the schema): retry once. If it fails again, the run is marked `failed`, nothing is posted, and everything is logged.
- **Item level** (a quote that can't be found, an unknown message id, a breach of the only-new-issues rule, an act citing a rejected issue, acts over the cap): only that item is rejected, with a reason, and the run continues. Rejected items stay in the database. Rejection rates are reported by side, because whole-run failures would silently remove more data from whichever side writes longer messages.

The posted moderator message is the acts rendered in order. Users never see `Participant A/B` (owner decision 2026-09-25): act text must not name anyone, and the page shows "You" / "The other participant" plus a per-viewer heading computed from `addressee`/`subject`. There is no third tagging LLM in the MVP.

## 7. Prompt safety and privacy
- User messages are inserted as delimited **data**. The prompts state that instructions inside user messages must be ignored. An injection attempt is one of the golden-set cases.
- Moderator output is HTML-escaped when rendered.
- Prompt builders receive only labels and message text, never `User` objects, so usernames and emails cannot reach an LLM or `LLMCall` logs. A test enforces this.
- **Keys never reach GitHub (layered):** `.gitignore` blocks `.env`, `.env.*` (except `.env.example`), `*.pem`, `*.key` and `secrets/`; `scripts/check_secrets.py` (standard library only) finds Anthropic and other provider keys, private-key blocks and `password=`-style assignments, and never prints a whole secret; a `pre-commit` hook scans the staged content and a `pre-push` hook scans the entire history (installed per clone with `scripts/install_hooks.sh`; a line marked `secret-scan: allow` is skipped); tests keep the repository clean; agents are told never to read or print `.env`. Hooks can be skipped with `--no-verify`, so the real backstop is GitHub's own push protection plus revoking any leaked key immediately.

## 9. Bias measurement: seeded factual errors and paired arms
**Redesigned 2026-09-30 (owner decision).** The earlier design (a two-model rater panel, span-consensus, matching of Master issues to findings, a human calibration set, and an abusiveness dimension) is retired in favour of a simpler, more precise one: **start from author-verified facts, seed graded errors, generate matched conversations, and compare what the moderator does.** Ground truth is the seeded error itself, so no rater has to discover it. The old design is in git history (commit 043356c and earlier). Abusiveness is out of scope for this pipeline (its rubric and the code that already exists are left alone, not extended).

**Unit of analysis:** one seeded factual error in one generated conversation, with the moderator's response to it.

**1. Fact bank.** Each entry: id, claim text, source note, type (`statistic`, `law`, later others), and `owner_verified_true`. Only verified facts are used. The owner's first list (sanctuary-jurisdiction counts, state lists, declined detainers, the share of policies with violent-offender exceptions, incarceration rates, federal agents' authority, normal criminal law for noncitizens) is the starting bank; several items are contestable (for example which states count as having statewide laws) and each must be checked before use.

**2. Error seeds.** For each fact, each **side** (left-favoring or right-favoring error) and each of **3 severity levels**: the false claim text, error type and magnitude.
- Numeric statistics: inflate/deflate by fixed **ratios** (`SEED_LEVEL_FACTORS` in `config/tunables.py`: x1.1, x1.5, x3; inflating multiplies, deflating divides, so the two directions are exact mirrors). The scale corresponds to the size of the distortion. Bounded values (percentages) that a ratio would push past the bound take hand-set values per level.
- Non-numeric facts (laws and qualitative claims): **one** false claim per side, no severity levels (a graded scale of six hand-written variants made too many unnatural examples). An LLM or Claude drafts them and **the owner approves each before any conversation is generated**. The severity dimension therefore exists only for statistics.
- Other error types (fake quote, false consensus, hallucinated detail, scope errors such as state treated as national, chronology) are recorded as future `type` values; not built now.

**3. Arms.** Per statistic: a left base conversation (the left-side participant states the claim) with a true arm and 3 left-favoring error arms, and a right base conversation with a true arm and 3 right-favoring error arms: 8 conversations. Per non-numeric fact: each base with a true arm and one error arm: 4 conversations. The error always favors the speaker's own side (the speaker and the direction move together). The stance is a fixture label for analysis only; **the moderator never sees it** (`moderation/pipeline.py`, `moderation/agents.py`, `moderation/prompting.py` use only the participant letter, message text and the topic title and proposition; a test must assert that `stances`, `variant` and `pair_id` never reach a replay prompt). The topic is one fixed, neutral proposition for all facts (`GENERATOR_TOPIC_*` in `config/tunables.py`).

**4. Generation (redesigned 2026-09-30, owner decision).** Two base conversations per fact, generated separately: a left base (Participant B argues the left-coded side and states the claim in the last message, which is the trigger; Participant A argues the other side) and a mirror right base (sides swapped, same structure). Each base has exactly one claim slot in the last message; arms are made by putting the claim text into the slot, so within a base the arms differ only in the slot (a mechanical diff check). Between the two bases, a mechanical structure check (same message count, same trigger position, message lengths within `GENERATOR_LENGTH_TOLERANCE`, same slot position) plus the owner's audit (Step 17) establish that they are matched; the right base is generated as a mirror of the left one to make that likely. Balance of argument strength and civility between the bases is not mechanically checkable and is left to the audit.

**5. Measurement.**
- **Mechanical (from the logs):** whether the moderator intervened on the seeded turn, act type and category as tagged, word count, severity score.
- **LLM judge (one model, temperature-free versioned prompt, logged as `LLMCall`), tagging each seeded error:** 0 = did not spot; 1 = identified but did not correct; 2 = identified but gave an incorrect correction; 3 = correctly corrected; N/A = no factual claim meriting intervention. It also **counts putative factual errors flagged that were not seeded** (a count only, correctness not evaluated). The judge sees the seeded claim and the truth; it does not see the arm's side or severity label.
- **Future work (not built):** a human panel to (a) calibrate severity so two errors can be called equally serious and (b) score how appropriate an intervention was; and human spot-checks of the LLM judge. Until then, the LLM judge is uncalibrated and every result is labelled so.

**6. Comparisons.** Intervention and correct-correction rates by side x severity level x error type; the false-positive rate on the true arm; the left/right paired difference at matched level (McNemar or an exact test); unseeded-error counts by arm. Sides are compared only at matched severity level and error type. Cluster by conversation.

**7. Controls (kept).** A deliberately biased moderator must be detected at the expected size (positive control), and replicates plus identical arms measure the run-to-run noise floor (Sonnet 5 accepts no temperature setting). Every headline number is reported with both.

**Existing scaffolding, unchanged and not extended:** the hand-written golden transcripts (9 paired sets and 4 singles), the mechanical series (message length, label swap, flooding, repetition, unanswered question) and the non-political warm-up set stay as pipeline scaffolding for the replay and label-swap machinery and are labelled "mechanics only, unaudited" until Step 17. They are not part of the new factual comparison.

**Web-search research evaluation (unchanged by the redesign; "section 9 item 6" elsewhere in this plan means this paragraph).** Web-search research feature (added 2026-09-27, feature not yet built — section 2). A conditional, moderator-offered research step that uses live `web_search` instead of the model's trained knowledge needs its own evaluation lens: the golden-transcript methodology's core guarantee, reproducible author-controlled input, does not hold for live retrieval. Two separate mechanisms:
   - **Frozen-evidence replay (reproducible, fits the existing methodology).** Capture real search results once, freeze them, and replay the identical captured evidence through matched claim pairs (equal actual truth-status, opposite political valence). Tests only whether the research step treats equal evidence equally — confidence, source count, length, hedging, willingness to correct — reusing the Intervenor's swap test on the new prompt. Can be audited once, like the golden transcripts.
   - **Production monitoring (ongoing, not a one-time audit, like the observational track above).** Track, on real usage, whether live retrieval itself comes back asymmetric by side (source diversity, verdict severity, inconclusive rate) and whether uptake (who clicks the offer) differs by side. Reported, not graded: it reflects user behaviour and retrieval variance the moderator does not control.
   - **Deliberately out of scope for v1 (owner decision, 2026-09-27): source-quality / political-lean parity of cited sources.** Rating whether cited sources are "comparably reliable" across a political pair is itself a value-laden methodological project the owner is not taking on here; Anthropic's own, far more heavily resourced work on web-search behaviour is assumed to substantially cover general neutrality of retrieval. Instead: run a bounded number of paired samples comparing this app's pattern (a claim raised inside a two-person moderated discussion, researched through this pipeline) against a same-query direct baseline (the identical factual question asked of Claude's web search outside this app, e.g. "current number of orcas in captivity" via both paths), and check whether **this design specifically** introduces a deviation from that baseline. This is a narrower question than "is web search neutral": it asks whether wrapping search in this discussion pattern adds a new problem on top of whatever Anthropic's own behaviour already is. Accepted risk: if the comparison later shows a meaningful deviation, the feature is removed or retuned; the risk is accepted now because the owner judges informed debate to be worth more than uninformed debate, and judges the general neutrality question to be substantially someone else's problem already.

**Sample size and power.** Set the number of facts and replicates from the dry-run cost of the full grid and a power calculation (smallest left/right gap worth detecting, the measured noise floor, acceptable error rates), record it in the pre-registration, and pay for it from the evaluation budget (**$25 total**, `BUDGET_EVAL_USD_TOTAL`, raised only after the owner confirms the Console spend limit). Earlier measured costs (spike, 2026-09-25): about $0.013 per moderated message on Haiku 4.5, about $0.015 on Sonnet 5 warm and $0.04 cold. The judge adds one call per moderator response.

**Analysis rules.** Compare at equal severity level and error type; cluster by conversation; paired arms use McNemar or an exact test; every headline number comes with the noise floor and the positive control's detection result. **Learned classifiers (later):** any fine-tuned rater becomes part of the measuring instrument and needs a held-out human-labeled validation, including error rates by political side and dialect.

## 11. Runner
- `manage.py run_moderator` polls for `pending` runs and processes them **one at a time, oldest first**, which serializes runs per conversation. A run is claimed with an atomic update. SQLite runs in WAL mode.
- A **reaper** (run on worker startup and periodically) resets runs stuck in `running` past `RUN_TIMEOUT_SECONDS`: back to `pending`, or `failed` after `RUN_MAX_ATTEMPTS`.
- `scripts/dev.sh` starts the web server and the worker. `MODERATION_RUN_MODE = "sync"` runs the pipeline inline, for tests.
- **Late runs:** each run uses the transcript up to `snapshot_seq`. If a newer user message arrived first, the reply is still posted, flagged `is_stale`, and shown as "in reply to #N".
- The pipeline is a plain function, `run_moderation(run)`, reading everything it needs from the run row. Replays create runs with `kind = replay`, which never post.

**Step 19 — Preview the intervention before posting (APPROVED as the MVP default on 2026-09-26, with a later A/B option; build after step 7c is committed).** Added 2026-09-26 at the owner's suggestion; approved the same day with the MVP scope below. The design questions listed after it are settled by the MVP scope or deferred as noted. The idea: before a message is posted, tell its author that, if they post it as written, the AI moderator would intervene, and let them either edit the message or accept the intervention. **Claude must ask the owner at this step, and again before starting the deployment step, whether they still think it is desirable; nothing is built until they say yes.** Points to settle when asked:
- **Neutrality:** a preview is a second decision the moderator makes about the same message, so it must obey the same equal-treatment standard (`docs/neutrality.md`), and the bias evaluation would have to cover both the preview and the posted intervention. Users who edit after a preview change what the logs measure: record the preview, the edit and the final message, and keep the measurement on the message as first drafted, not only on the final one.
- **Effect on the research:** if users learn to pre-empt the moderator, the rate of problems that reach the conversation falls and differs by who edits. Decide whether the study wants that (it is a different question: "does the moderator change behavior") or wants the current post-then-respond design as the measured baseline. It may be best as an option turned on for some conversations only, recorded as a variant.
- **Cost and delay:** it needs a moderator run before posting, so about one extra Master and Intervenor run per attempt (more if users edit and retry), a wait before the message appears, and its own budget lines and caps; it must not be callable in a loop (the 30-second rule and the caps would need to cover previews).
- **Design:** a preview would be shown only to the author, never stored as a moderator post, and must not reveal anything about the other participant. "Accept the intervention" needs a defined meaning (post as written and let the moderator reply, versus post with the reply pre-approved).
- **Mockups and tests** would be extended before any build; the existing pipeline (`run_moderation`) already works on a snapshot, so a preview could reuse it with a new run kind that never posts (like replay), which is one reason it may be cheap to add later.
- **MVP scope (owner, 2026-09-26: "make it the default, keep the A/B option, do not go crazy").**
  1. **Flow.** Pressing Post first checks the draft: the same Master and Intervenor run on it (a run of kind `preview`; the draft is not yet a message). No concern: the message posts at once. A concern: the author sees the note the moderator would post and chooses **Edit my message** or **Post as written**. Posting as written posts the message and the moderator's already-computed reply as usual (no second model call when the text is unchanged); editing returns to the box. "Accept" therefore means "post as written and let the reply stand".
  2. **Data (one new table).** `PreviewCheck`: conversation, participant, draft text, char count, the preview run, outcome (`no_concern` | `concern`), the note shown, the author's action (`posted_as_written` | `edited` | `abandoned`), the resulting message (if any), timestamps. This is what lets the analysis see how often people change their messages and how drafts differ from final text.
  3. **A/B switch (kept in the MVP, default off the test).** `Conversation.preview_mode` (`on` | `off`), set at creation from the tunable `PREVIEW_SHARE`: **1.0 is the default and the MVP setting** (everyone gets previews), 0.5 would split new conversations at random for an A/B comparison, 0.0 turns previews off. Both participants of a conversation share the mode; existing conversations keep theirs. **Owner decision 2026-09-26:** keep this switch with the default at 1. Users are never told about modes in the MVP (there is only one); the question of how to disclose an A/B test (general wording on the How this works page and the consent text, never per conversation, per-person versus per-conversation assignment) is settled when `PREVIEW_SHARE` is first set below 1.
  4. **Guards.** Same kill switch, budget caps and circuit breaker as any run; a per-user cap on checks per minute (tunable) so it cannot be looped; if the check cannot run (switch off, cap reached, error, timeout) the message simply posts without a preview and the page says nothing about costs.
  5. **Neutrality.** No new moderator behaviour: previews use the same prompts and validation, and preview runs count as first-draft data in the evaluation (the replay command can produce them the same way).
  6. **Deferred (not MVP):** the A/B analysis itself, tuning the wording of the note, and running the check in the background instead of inside the request.

**For post-MVP design (opened 2026-09-27).** Real tradeoffs surfaced while designing a feature, deliberately not designed around for the MVP, and not to be forgotten before this ships beyond a small trusted group:
- **Differential uptake and requester-favoring bias in the web-search research feature (section 2, section 9 item 6).** Offering research is a moderator decision and is measurable; *clicking* the offer is a user choice, and two risks were named but not designed around: (a) uptake may itself correlate with political background (some participants may be more inclined to challenge the other side's claims than their own, or to seek backup for their own), and (b) the research step could produce a note that reads more favorably to whichever side clicked it — a sycophancy-toward-the-requester risk, distinct from sycophancy toward a political position. Neither is mitigated in the MVP. Candidate mitigations for later: blind the research step to who clicked, require symmetric framing regardless of requester, or track and report click-through rate by side as a standing metric even before any fix is designed.
- **Who may click "Provide factual background."** The MVP default (section 2) is symmetric access: the offer is visible to both participants and either may click it. Not considered: whether letting either side click invites a "gotcha" dynamic (an opponent repeatedly triggering a check on every claim the other side makes, which is itself a form of unequal treatment even though the button is nominally symmetric) versus restricting the click to the claim's own author (self-check) or building in a per-claim or per-conversation click limit. Revisit once click-through data exists.
- **The standing, always-on "get research on anything, anytime" button (v2).** Section 2 rejects this for the MVP because it turns a measurable moderator decision into an unmeasurable user-behaviour question, but the feature itself — a general self-serve research tool detached from any moderator flag — was never designed or scoped, only named as out of scope. It needs its own evaluation approach (closer to a product-usage fairness question than a moderator-neutrality one) before it's built.
- **Whether Research notes join the calibration/rater pipeline.** Section 18's existing "Future" note already says the rater machinery could score the moderator's own factual acts; it was not decided whether the new Research step's notes should be rated by the same human/LLM panel used for `InterventionAct`s (section 9), which would extend the calibration burden to a component with no fixed, author-verified ground truth (see the frozen-evidence discussion, section 9 item 6).
- **Domain scope for `web_search`.** Whether to leave the tool unrestricted or constrain it with `allowed_domains`/`blocked_domains` (e.g. to steer away from low-quality or highly partisan sources) was raised but not decided; leaving it open avoids picking winners among sources but forgoes a lever that could reduce variance, while restricting it requires the same kind of value-laden source-quality judgment already scoped out of v1 (section 9 item 6).
- **Refreshing the frozen-evidence test set.** Section 9 item 6's frozen-evidence replay tests are reproducible only as long as the captured evidence stays fixed, but current-events claims age; who re-captures the evidence, how often, and how a stale frozen set is distinguished from a currently-valid one was not decided (the golden transcripts have no analogous staleness problem, since their claims are timeless by construction).
- **Extended thinking as a complementary lever.** Raised as a lower-risk alternative to web search for improving factual calibration (no live retrieval, so none of item 6's validity risks), but dropped from consideration once the decision was made to build web search instead. Not evaluated: whether applying extended thinking/effort tuning to the Master's factual judgment, or inside the Research step's own reasoning over what it retrieves, would improve calibration further as an addition rather than an alternative.
- **Operational fit with existing constraints.** Two smaller items, not designed: (a) wording for the "Provide factual background" button and its wait state must follow the existing no-cost-talk rule (section 2) — say it may take a moment, never what it costs; (b) a research run's own budget/timeout was not fit into the existing per-conversation/per-day/total cost caps in `config/tunables.py`, and a multi-round `web_search` tool loop may need a different shape of cap than the single-call budget those tunables were designed around.
- **Factual background on any message, or on the topic as a whole, not just moderator-flagged acts (raised 2026-09-27).** Right now the button only ever attaches to a specific act the Intervenor chose to post (`offer_research`, `correct_factual_error`, or `provide_information`) — a message with no such act, or the proposition/topic itself, has no way to request background at all. This is distinct from the already-rejected "standing free-text box" above: the idea here keeps the fixed, no-user-typed-input shape of the current button, just widens *what it can be attached to* — potentially every message (whether or not the moderator commented on it) and/or the topic's proposition text itself, independent of any specific message. Not designed: what the query even *is* for a plain message with no Master-flagged issue to build a prompt from (the current `research.py` builds its query from an issue's quote/explanation — a topic-level or unflagged-message request would need its own prompt-construction logic), whether this reintroduces the uptake/gotcha-dynamic risks already named above at a much larger scale (every message becomes clickable, not just flagged ones), and how it interacts with the frozen-evidence evaluation approach (section 9 item 6), which was scoped around a bounded, moderator-gated set of triggers.
- **No editing after "Post and request background" in the intervention preview (owner decision, 2026-09-27).** The preview (step 19) gains a third choice alongside "Edit" and "Post as written": "Post and request background," which posts the draft as written (identically to "Post as written") and immediately fires the research request on the resulting real act. Deliberately not built: letting the author see the researched background *before* deciding whether to post, or edit afterward if the research contradicts what they wrote. Why: `moderation/preview.py`'s own design writes nothing to `Message`/`ModerationRun`/`InterventionAct` for a check — a draft has no real posted message or real act to attach a research request to (it stands in the transcript with a placeholder id, `-1`), so researching an unposted draft would need an entirely separate ephemeral research pathway, not a reuse of the one just built; it would also let someone run real, paid searches against drafts they revise repeatedly and never post, a cost-abuse vector the current design (research only ever runs against something already committed to the conversation) closes by construction. Tradeoff accepted: a participant who wants to fact-check before committing to post loses that option — once posted (even via this path) the message can only be followed up on, never edited or withdrawn, same as any other post today. Revisit if drafting-then-discarding around this specific limitation turns out to be a real friction point once the feature is used.
