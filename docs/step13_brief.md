## What it does
The replay command loads scripted transcripts from `golden/transcripts/*.json` (or `--directory`) into the database as **synthetic conversations**, then creates and executes `kind="replay"` moderation runs on them, so the whole moderation pipeline is exercised on scripted input with known ground truth. Replay runs never post a moderator message (already enforced by the model and the pipeline), so the scripted transcript is never contaminated by moderator output.

`moderation/replay.py` (pure library, importable, tested without the command):
- `load_experiment(name, transcripts, *, assignments="as-is", replicates=1, kind="replay") -> ExperimentPlan`: creates or reuses `forum.Experiment(name=..., kind="replay"|"paired", description, config)` (config records the transcript ids, assignments, replicates, tunables in force, and the prompt fingerprint from `moderation.agents.prompt_fingerprint()`), and for each transcript and each requested label assignment creates or reuses one synthetic `Conversation` (`source="synthetic"`, `experiment`, `pair_id` and `variant` from the file, `label_seed` recorded, `status="closed"`), its `Participant` rows (`user=None`; labels A and B), and its `Message` rows (`author_type="user"` for participants, `moderator` for the scripted moderator messages of a series transcript, `planted` from the file, `char_count` computed with the project's counter). **Idempotent**: running twice with the same arguments creates no new conversations or messages (the builder chooses the key, records it in `Experiment.config`, and documents it).
- **Label assignments** (`"as-is"`, `"swapped"`, `"both"`): "swapped" gives the same text to the other participant label (author A's messages become label B and vice versa); nothing else changes. Both assignments of a transcript share `pair_id`; each is a separate conversation with its own stored `label_seed`.
- The same limits as real users: a transcript with more than `MAX_USER_MESSAGES_PER_CONVERSATION` user messages, or a message over `MAX_MESSAGE_CHARS` (count with the project's counter), is rejected with a clear error naming the file and message (the spike's validation already checks some of this; do not weaken it).
- `plan_runs(experiment_plan, *, replicates) -> list[RunSpec]`: for each conversation, one run per (trigger message, replicate) where the trigger is the message the spike uses as the trigger for that transcript (read `run_transcript` and `validate_transcript` to see how; the builder documents it). `snapshot_seq = trigger.seq_no`.
- `execute_runs(specs, *, max_usd, model_overrides=None, on_result=None) -> ReplayReport`: creates `ModerationRun(kind="replay", replicate=k, status="pending")` rows (skipping specs that already have a `done` run with the same conversation, trigger and replicate, so an interrupted experiment can be resumed at no extra cost), and executes them **one at a time in-process** by calling `moderation.pipeline.run_moderation(run)`, stopping cleanly when the next run's worst-case cost estimate would push the spend over `max_usd` (report the remaining specs as `not_run`). It never posts, never touches live runs, never calls the API when `LLM_ENABLED` is False (runs then end `skipped_disabled`, which the report counts). Spend comes from the `LLMCall` ledger (`purpose="replay"`), not from estimates.
- `factors(conversation) -> dict`: the series factor values computed by code from the stored transcript with `moderation.series.compute_features` (never hand-labeled), stored on the run's `config_snapshot["factors"]` at run creation.
- `ReplayReport`: counts by status/failure_reason, total cost, per-transcript cost, `not_run`, and a printable summary.

`manage.py replay`: options `--experiment NAME` (required), `--directory DIR`, `--set PATTERN` (glob on transcript ids, repeatable), `--assignments {as-is,swapped,both}` (default both), `--replicates N` (default 1), `--max-usd X` (required unless `--dry-run`; must not exceed the remaining evaluation budget, `BUDGET_EVAL_USD_TOTAL` minus spent), `--dry-run` (prints the plan: transcripts, conversations that would be created, runs, and the worst-case cost estimate from `spike.estimate_worst_case`; **writes nothing and makes zero API calls**), `--live` (without it the command runs with `LLM_ENABLED` False, so everything is recorded `skipped_disabled`; with it, mirror exactly the spike command's process-local override and its confirmations). The command prints the summary, never prints keys, and never reads `.env` directly.
