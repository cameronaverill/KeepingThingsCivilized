## The new behaviour (fixed)
- **Register** (`accounts:register`): username, password, password again. Validation: the existing username rules (ASCII letters, digits, `_`, `-`, 3–30 chars, unique ignoring case and Unicode form via `username_key`), the existing password validators (minimum length, common, similar to the username, all digits), and the two passwords must match. On success the user is created **active**, `django.contrib.auth.login()` is called (with the axes-compatible backend the login view uses; check how `authviews.LoginView` authenticates and mirror it), and the response redirects to `forum:home`. **A taken username** re-renders the form with the field error "That username is taken." (compare via `username_key`, not exact case). Rate limiting of registrations: none new (the site's other limits apply); registration must not create an account on any validation failure (atomic).
- **Register page text** (this is user-facing and will be reviewed by the owner; use exactly these sentences): title "Create an account"; intro "Choose a username and a password. You do not need an email address." ; a note under the password fields: "There is no password reset by email. If you forget your password, ask the person running this site to reset it."; button "Create account"; link "Already have an account? Log in".
- **Login / logout / change password** stay: same axes lockout, same generic error, same 429 lockout page. Remove every mention of confirming email, resending a link, "email not confirmed", and "Forgot your password?" from templates, views and messages. `LoginForm` no longer has an "unconfirmed" state (accounts are active). Password change (logged in, old password required) stays. **Password reset by email is removed**: the reset views, URL names (`password_reset`, `password_reset_done`, `password_reset_confirm`, `password_reset_complete`), templates, the email templates and their settings.
- **Removed pages**: check-email, confirm (all four outcomes), resend. Their URL names disappear (`accounts:check_email`, `accounts:confirm`, `accounts:resend`); a request to an old path is a normal 404.
- **User model:** `email` stays as a column but becomes optional: `EmailField(blank=True, default="")`, never asked for, `REQUIRED_FIELDS = []` (so `createsuperuser` asks only for username and password). `email_key` is still filled by `save()` (empty string for no email) but is unique **only when non-empty**: migration `0003` drops `unique=True` on `email_key` and adds `UniqueConstraint(fields=["email_key"], condition=~Q(email_key=""), name="accounts_user_email_key_unique_when_set")`, alters `email` to `blank=True, default=""`, and must reverse cleanly (reverse migration test on a populated database). `save()` no longer requires an email (remove the "Enter an email address." error); the "email already exists" collision check applies only when an email is given. `email_verified_at` stays, unused. `create_user`/`create_superuser` work with no email. The existing `username_key` behaviour is unchanged. Existing rows (with emails) keep their data.
- **Admin:** search by email stays; the list may show a blank email. The admin still has no password display.
- **Other code:** anything else in the repo that reads `user.email` must tolerate an empty string (exports with `--include-identities` print it as `""`; the pseudonym is unaffected). `moderation/breaker.py` ALERT_EMAIL and the mail backend stay (that is the circuit-breaker alert, unrelated to users).
