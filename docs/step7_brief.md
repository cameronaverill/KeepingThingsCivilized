## Owner decisions this step implements (plan section 2)
- Users create their own propositions; each appears **immediately**, newest first, with a search box; the home page shows the proposition text only (a link), with no thread lists or counts.
- The **A/B labels are never shown to users.** They see "You" and "The other participant". Labels stay internal (random assignment when a conversation fills, `label_seed` stored).
- **Only the two participants can read a conversation.**
- A conversation with one person is **waiting**; it **never expires**. Either participant can **end** a conversation (closes it for both, read-only, kept in the logs); a waiting conversation's creator can end it too.
- One participant can post several messages in a row; there is **no turn-taking rule** and no "not your turn" rejection.
- The 30-second gap between a participant's own messages stays; 30 user messages per conversation; 3,000 characters per message; 200 characters per proposition; 20 propositions per user per UTC day.

## 7a: `forum/services.py` and friends (the only code that creates propositions, conversations, participants and user messages)
Migration `forum/migrations/0002_*` (small, reversible, `makemigrations --check` clean): `Topic.created_by` (nullable FK to the user model, PROTECT; null = seeded), `Topic.hidden` (bool, default False), `Topic.title` may be blank (unique only when non-blank, a conditional `UniqueConstraint`, replacing the current unconditional unique), a database `CheckConstraint` that `proposition` is not empty; `Conversation.ended_by` (nullable FK to `Participant`, PROTECT), `Conversation.ended_at` (nullable datetime); the choice checks from 0001 stay. Existing 4a tests must keep passing except the app-shape file above.

**`PostRejected(Exception)`** with attributes `code` (a stable string), `message` (the user-facing text, plain words, naming the reason and what to do next), `retry_after` (int seconds or None), and `details` (dict). The views show `message` next to the form and keep the user's text. **No path fails silently or with a generic or internal error text.** Codes and their required wording (exact phrasing for each is pinned by tests through key phrases; use the plan's text):
- `empty` ("Your message is empty.") for messages and propositions.
- `too_long` ("Your message is 3,412 characters; the limit is 3,000. Please shorten it by 412 characters. Messages are capped to keep the discussion readable and to keep the AI moderator's running costs low." and the proposition equivalent naming the 200-character limit).
- `too_fast` ("Please wait 12 more seconds before posting again. Messages are limited to one every 30 seconds to keep the discussion readable and the AI moderator's running costs low."), `retry_after` = whole seconds left, measured from **the same participant's previous message** on server time (`django.utils.timezone.now`, patchable in tests).
- `conversation_full` ("This conversation has reached its limit of 30 messages and is closed. You can start a new one.") and `closed` ("This conversation is closed." plus who ended it if it was ended: "You ended this conversation." / "The other participant ended this conversation." and what to do next), `waiting` ("You can post once someone else joins."), `not_participant` ("You are not a participant in this conversation."), `daily_limit` for propositions ("You have created 20 propositions today, which is the daily limit. Try again tomorrow (UTC), or pick an existing proposition to discuss."), `duplicate` for propositions (a proposition whose text matches an existing visible one after NFKC, casefold and whitespace normalisation: "This proposition already exists. Choose it from the list." with `details["topic_id"]`), `too_many_open` (`MAX_OPEN_CONVERSATIONS`: "You already have 5 open conversations. End one before starting another."), `hidden` (a hidden proposition cannot be entered).
Use `forum.limits.count_message_chars` for every length check. Numbers in the messages come from settings, never hard-coded.

Functions (all plain functions taking model instances; user must be an authenticated user; database work in `transaction.atomic()` and, where a race matters, the project's IMMEDIATE mode so two simultaneous requests cannot both win):
- `create_proposition(user, text) -> Topic`: normalise (strip, collapse inner whitespace, NFC), checks (`empty`, `too_long`, `duplicate`, `daily_limit` counted per UTC day from `Topic.created_by`/`created_at`), creates the visible `Topic` (title blank, description blank, `leans` `{}`).
- `enter_proposition(user, topic) -> Conversation`: the pairing rule in one place: (1) the user's own `open` or `active` conversation on this topic -> return it; (2) else the oldest `open` (waiting) conversation on this topic with exactly one participant who is **not** this user -> join it: create the second `Participant`, **assign the labels A and B at random** (`random.Random(seed)` with a stored `Conversation.label_seed`, fresh from `secrets`; record `join_order` separately from the label) and set status `active`; (3) else create a new `open` conversation with one participant (label assigned when it fills; a waiting participant's label is set at fill time, so store the waiting participant with a placeholder that the fill step replaces: the builder chooses the mechanism, e.g. label assigned at fill for both, and documents it; the 4a constraints must still hold). Refuses hidden topics and `too_many_open`. Never pairs a user with themself.
- `post_message(user, conversation, text) -> Message`: checks in this order: not a participant, closed, waiting, empty, too long, too fast, conversation full (this message would exceed `MAX_USER_MESSAGES_PER_CONVERSATION`; when the 30th message is posted the conversation is closed after it); creates the `Message` (author type user, the participant, `in_reply_to` optional) and, **in the same transaction, exactly one pending live `ModerationRun`** for it (`snapshot_seq` = its `seq_no`, `kind="live"`, status `pending`); after commit, if `settings.MODERATION_RUN_MODE == "sync"`, call `moderation.pipeline.run_moderation(run)` **imported lazily inside the function** (step 5 is being built in parallel; in `worker` mode do nothing else). A rejected post saves nothing and creates no run. Nothing here ever creates a run for a moderator message.
- `end_conversation(user, conversation) -> Conversation`: a participant of an `open` or `active` conversation closes it, sets `ended_by`/`ended_at`; not a participant -> `not_participant`; already closed -> `closed`.
- `conversation_view(user, conversation, after_seq=0) -> dict` in `forum/viewmodels.py`: refuses non-participants (`not_participant`); returns `{"status", "proposition", "you_ended": bool|None, "ended_by_other": bool|None, "messages": [...], "moderation_notice": str|None, "message_count", "message_limit", "waiting": bool, "can_post": bool, "cannot_post_reason": PostRejected-like dict or None}`. Each message dict: `seq_no`, `kind` (`"you"`, `"other"` or `"moderator"`), `text`, `created_at`, and for moderator posts `heading`, computed per viewer from the acts' `addressee`/`subject` of the run that posted it: "About your message N" (subject is the viewer's label and the source message is theirs), "About the other participant's message N", "For both of you" (addressee `all` or subject `both`), "About the conversation" (subject `none`); N is the source message's `seq_no`. **No label letter and no username or email ever appears in the view dict.** `after_seq` returns only newer messages (for polling). `moderation_notice`: from the latest run of the conversation: `skipped_budget` -> "The AI moderator has reached its spending limit (today's, this conversation's, or the site's) and will resume when it resets; messages are still posted." choose the exact variant from `failure_reason`/budget state if available, else the generic sentence; `skipped_disabled` -> "AI moderation is switched off right now; your messages are still posted."; `failed` -> "The AI moderator ran into a problem on the last message; your messages are still posted." Never any internal error text.
- `forum/admin.py`: register `Topic` with the propositions listed, `hidden` toggle and a "Hide selected propositions" / "Unhide" action, `created_by` shown; hiding keeps conversations. Other models: read-only registration is optional (step 9 owns the full admin).
