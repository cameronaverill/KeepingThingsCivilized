## What it does
Before a message is posted, the author's DRAFT is checked by the same Master and Intervenor that moderate live messages, with the same prompts and the same validation. If the moderator would step in, the author can see the note first. If the author then posts the draft **unchanged**, the message's live moderation run **reuses the already-computed model outputs** (no second model call), so the reply that appears is exactly the one previewed.

## Models (moderation app, migration 0005)
- `PreviewMode`: `conversation` (`IntegerField`, plain id, unique; do not FK into forum from a new migration), `mode` (`on` | `off`), `assigned_at`. Created lazily the first time a conversation is checked: `mode = on` with probability `PREVIEW_SHARE` (a new tunable, default `1.0`; `0.0` is always off), drawn with `secrets` (not `random`) and stored, so later changes of the tunable never change existing conversations. Both participants of a conversation share the mode (it is per conversation).
- `PreviewCheck`: `conversation` (plain integer id, indexed), `participant` (plain integer id), `draft_text`, `char_count`, `draft_sha256` (of the normalised draft: CRLF to LF, NFC, stripped, exactly as `forum.limits.count_message_chars` normalises), `snapshot_seq` (the highest message `seq_no` in the conversation when checked), `mode` (`on`|`off`), `outcome` (`no_concern` | `concern` | `unavailable`), `unavailable_reason` (blank | `off` | `rate_limited` | `llm_disabled` | `budget` | `breaker` | `refused` | `structural` | `api_error`), `note_texts` (JSON list: the valid act texts shown to the author, empty for no concern), `master_output` and `intervenor_output` (JSON, the validated model outputs with the draft's placeholder message id, null when unavailable), `llm_call_ids` (JSON list of the ledger rows), `action` (blank until resolved, then `posted_as_written` | `edited` | `abandoned`), `resulting_message_id` (nullable integer id), `reused_by_run_id` (nullable integer id), `created_at`, `resolved_at`. Database rules: `outcome` and `action` choices enforced with CHECK constraints; a resolved check has `resolved_at`.

## `moderation/preview.py` (fixed interface)
- `preview_mode(conversation_id) -> "on" | "off"` (creates the `PreviewMode` row on first call).
- `check_draft(conversation, participant, draft_text, *, now=None) -> PreviewCheck`. Precondition (the caller validates): the draft passes the same rules as a post (participant, open/active, non-empty, length); do not duplicate those rules here. Steps: (1) mode off: a check with `outcome="unavailable"`, reason `off`, and NO model call; (2) per-participant rate cap: more than `PREVIEW_MAX_CHECKS_PER_MINUTE` (new tunable, default 6) checks in the last 60 s: `unavailable`/`rate_limited`, no call; (3) build the transcript exactly as `pipeline.build_transcript` would for a run triggered by the draft, with the draft as the newest user message of the participant's label and a placeholder message id (use `-1`), then call `agents.call_master` and `agents.call_intervenor` (`purpose="moderation"`, `run_id=None`, `conversation_id` set; the caps, kill switch and breaker apply as always); (4) validate the outputs IN MEMORY with the same validation code as the live pipeline (factor the pipeline's issue and act validation into shared functions that work on plain data, changing no pipeline behaviour: every existing pipeline test must pass unchanged); (5) `concern` when the Intervenor decides to intervene and at least one act is valid, `no_concern` otherwise; `note_texts` are the valid act texts in order. Any `LLMRefused`, `LLMAPIError`, `StructuralFailure` or timeout-like failure is caught and recorded as `unavailable` with the matching reason; nothing propagates to the caller. Nothing is written to `Message`, `ModerationRun`, `Issue` or `InterventionAct` by a check.
- `resolve_check(check_id, action, *, message_id=None)`: sets `action`, `resolved_at`, `resulting_message_id`; idempotent for the same action; refuses (ValueError) an unknown check, a bad action, or resolving twice with a different action.
- **Reuse in the live pipeline.** In `moderation.pipeline` (the live run for a user message), before the Master call, look for a reusable check: same `conversation`, same participant (the message's author), `draft_sha256` equal to the message text's normalised sha256, `snapshot_seq == message.seq_no - 1` (nobody posted in between), `outcome` in (`concern`, `no_concern`), not yet reused, created within `PREVIEW_REUSE_SECONDS` (new tunable, default 900). If found: use its stored outputs (replace the placeholder id `-1` by the message's id in issue and act references) instead of calling the model, skip the ledger, run the normal validation, storage and posting exactly as for a fresh answer, set the check's `reused_by_run_id`, and record `preview_check_id` in the run's `config_snapshot`. If not found (edited text, other participant posted first, expired, unavailable): the run behaves exactly as today. A reused result must be byte-for-byte what a fresh run of the same outputs would store.
- Everything in the check is private to the author: nothing about previews, drafts or modes enters a prompt, an export or a log line (log lines carry ids and counts only, never draft text).
