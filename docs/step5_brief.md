## Interface between 5a and 5b (fixed; both build to it)
A **transcript** is a list of plain dicts, oldest first, at most the last `TRANSCRIPT_MAX_MESSAGES` messages up to and including `run.snapshot_seq`: `{"id": <Message pk>, "seq_no": int, "author_type": "user"|"moderator", "label": "Participant A"|"Participant B"|... for user messages, "Moderator" for moderator messages, "text": str, "created_at": datetime}`. The label of a user message is `"Participant " + Participant.label`.

`moderation/agents.py` (5a):
- `class StructuralFailure(Exception)`: raised when the model's output is unusable after one retry (invalid JSON or does not match the schema).
- `call_master(run, transcript, *, topic, already_raised=(), process_facts=None) -> MasterOutput` and `call_intervenor(run, transcript, *, topic, valid_issues, discussion_map=None) -> IntervenorOutput`. `topic` is the `forum.Topic`; only its proposition (and title when present) reaches the prompt. Each builds the system prompt from `load_prompt`, the user input from `prompting.render_*`, and calls `llm.call` with `purpose="moderation"`, `agent="master"`/`"intervenor"`, the model and max tokens from tunables, `run_id=run.pk`, `conversation_id=run.conversation_id`, `prompt_version` set to the prompt's file name (`prompt.name`, e.g. `"master_v1"`, exactly as the spike records it), `cache_system=True` as the existing spike does. One structural failure is retried once (`attempt=2`); a second raises `StructuralFailure`. `LLMRefused` (budget, kill switch, breaker) and `LLMAPIError` are NOT caught here: they propagate to the pipeline. Prompts and inputs contain no usernames or emails (only labels, message ids, text).
- `prompt_fingerprint() -> dict`: `{"master": {"name", "sha256"}, "intervenor": {...}}` for the run's config snapshot.

`moderation/features.py` (5a):
- `process_facts(transcript) -> dict`: computed in code from the transcript, no LLM: consecutive messages per participant label (current run of the latest author, longest run), seconds between the last messages (from `created_at`), number of messages per label. JSON-serializable.
- `act_text_features(text) -> dict` with the same four values `InterventionAct.save()` computes (`char_len`, `word_count`, `is_question`, `quotes_participant`), by calling the same function the model uses if one is exposed, or, if the model computes them inline, by a tested copy asserted equal to the model's result; the builder reports which.

`moderation/pipeline.py` (5b): `run_moderation(run) -> ModerationRun` (see below). It imports `moderation.agents`, `moderation.features`, `moderation.label_check`.

## 5a details
- Both calls must be idempotent with respect to the database (the pipeline stores rows, not the agents module): `agents.py` writes nothing except the `LLMCall` ledger rows that `llm.call` writes.
- The Master's `issues` may cite message ids that are not in the transcript, quotes not in the message: that is the pipeline's job to reject, not agents.py's.
- Tests (5a tester, `tests/pipeline_agents/`, all with `FakeLLM`): the exact `llm.call` arguments for each agent (purpose, agent, model from tunables, max tokens, run and conversation ids, `cache_system`); the system prompt is the loaded prompt; the input contains labels, ids, text and the proposition and NO username or email (use users with recognisable names and assert absence); invalid JSON then valid JSON succeeds on the second attempt with two `LLMCall` rows; invalid twice raises `StructuralFailure`; schema mismatch counts as structural; `LLMRefused` (disabled, budget, breaker) and `LLMAPIError` propagate unchanged and make no retry; transcript truncation is applied by the caller, so agents.py must reject nothing but must not send more than it is given; `process_facts` on hand-built transcripts (runs, gaps, counts, single author, one message); feature equality with the model; `prompt_fingerprint` matches the sha256 of the files; the injected-instruction transcript (`golden/transcripts/single_injection.json`) reaches the model inside the data block, unchanged and escaped as `prompting` does.

## 5b details: `run_moderation(run)`
Behaviour, in order (plan sections 2 and 6):
1. **Re-check the trigger before any LLM call** (plan section 2, layer 3). If the run's trigger message is not user-authored (only possible if the database rules were bypassed), set `status="failed"`, `failure_reason="invalid_trigger"`, make no call, write no ledger row, post nothing, and return.
2. Set `status="running"`, `started_at`, `attempts += 1`. Build the transcript (last `TRANSCRIPT_MAX_MESSAGES` messages with `seq_no <= run.snapshot_seq`), `already_raised` from earlier valid issues of the conversation with their outcomes, `process_facts`.
3. **Master:** `agents.call_master(...)`. Then validate **each issue** (item level; a rejected issue is stored with `validity="rejected"` and a reason, and the run continues): unknown `message_id` (reason `unknown_message`); message not in the transcript window (`outside_window`); message is moderator-authored (`moderator_message`, plan section 2 layer 3: the Master never reports on the moderator); the **only-new-issues rule** (issue on a message older than the newest user message, of a type other than `repetition`, `strawman`, `process_violation`: `not_new`); quote not found by `locate_quote` (`quote_not_found`; store `quote_match="not_found"` and null offsets); duplicate `local_id` (`duplicate_id`); an `intensity` present for a type with no dimension (`intensity_without_dimension`, or keep and null it: builder decides and documents; the tester pins it). Valid issues store offsets and `quote_match` from `locate_quote`.
4. **Intervenor:** only if at least one valid issue exists; otherwise `decision="no_intervention"`, rationale `"no valid issues"`, and no second call. Else `agents.call_intervenor(...)` with the valid issues (as stored objects) and the discussion map. Validate: every valid issue gets exactly one disposition (a missing one is created as `declined` with reason `no_disposition`; an unknown issue id or a duplicate disposition is ignored and logged in the run's `error`); dispositions only on valid issues; acts: at most `MAX_ACTS_PER_INTERVENTION` valid acts (extras stored `rejected`, reason `act_cap`), an act citing a rejected or unknown issue is rejected (`bad_source_issue`), unknown source message ids rejected (`bad_source_message`), an act whose text **names a participant label or uses a viewer-relative reference** is rejected with reason `names_participant` (use `moderation/label_check.py: names_a_label(text)`), an `addressee` or `subject` not among the conversation's labels or `all`/`both`/`none` is rejected (`bad_label`), empty text rejected (`empty_text`). Acts are stored in order with features computed. `decision="intervene"` only if at least one act is valid; if the model said intervene but every act was rejected, the stored decision is `no_intervention` with the rationale kept and `failure_reason=""` (the rejections are in the acts).
5. **Posting** (live runs only, never for replays): if the decision is `intervene`, create the moderator message with `forum.Message.objects.create(conversation, author_type="moderator", participant=None, in_reply_to=trigger, content=<the valid acts' texts in order, separated by a blank line>)` and link it as `run.posted_message`. This code path never enqueues a run (a moderator message never triggers one, plan section 2 layer 1). At most one posted message per run, and exactly zero for replays.
6. **Finish:** `status="done"`, `finished_at`, `discussion_map`, `decision`, `rationale`, `config_snapshot` (models, max tokens, prompt fingerprint, relevant tunables), `is_stale=True` if a user message with `seq_no > snapshot_seq` exists at finish time (the run still posts). Everything database-writing happens in short transactions, **never one that spans an LLM call** (the guard's rule).
7. **Failure paths:** `StructuralFailure` from either agent: `status="failed"`, `failure_reason="structural"`, nothing posted, partial rows kept (issues from a successful Master call stay). `LLMRefused` subclasses: `BudgetExceeded`/`BudgetUnavailable` (and any spend-cap refusal) set `status="skipped_budget"`; `LLMDisabled` sets `skipped_disabled`; `BreakerOpen` sets `skipped_budget` with `failure_reason="breaker_open"`; nothing posted. `LLMAPIError` sets `status="failed"`, `failure_reason="api_error"`, error text scrubbed of anything key-like (use the existing scrubber). No exception escapes `run_moderation` except a programming error; the run row always ends in a terminal status.
8. `run_moderation` must be safe to call twice on a finished run (does nothing) and must refuse to run a run whose status is not `pending` or `running` (returns unchanged). Claiming, retry scheduling and the reaper are step 8, not here.

`moderation/label_check.py` (5b): move the regex and `names_a_label(text)` out of `spike.py` **unchanged in behaviour**: the alternatives are `\bParticipants?\s+[A-Z]`, `\b[A-Z]'s\s+(?:message|messages|reply|replies|claim|claims|point|points|statement|statements|argument|arguments|answer|answers|question|questions)\b`, and `\b[Tt]he other (?:participant|person|side|party)\b|\b[Aa]nother (?:participant|person)\b`, case-sensitive as before. `spike.py` then does `from moderation.label_check import NAMES_LABEL_RE, names_a_label` so the existing step 3 tests (which import them from `spike.py`) keep passing. ## Amendment (architect, 2026-09-26): rulings after the 5a/5b builders' reports

- `prompt_version` is the prompt's file name (`master_v1`), as the spike records it.
- The Intervenor writes `addressee`/`subject` as "Participant A"; the pipeline normalizes `Participant X` or `X` to the stored bare letter `X`. Addressee: a conversation label or `all`. Subject: a label, `both` or `none`. Anything else is `bad_label`.
- An issue citing an unknown message (or one later than the snapshot / in another conversation) is stored rejected, anchored on the trigger message, with the bare reason code. Analysis of rejected items by side must group them by `rejection_reason` and must not treat the anchor message as the message the model meant (the cited id stays in `LLMCall.parsed`).
- Duplicate `local_id`: the first stays valid; later ones are stored as `<id>#dupN`, rejected `duplicate_id`. `decision=no_intervention` with acts: the acts are stored rejected `decision_no_intervention`. `intensity_without_dimension` rejects the issue.
- A disposition of `acted` is kept even when every act for that issue is later rejected: it records what the Intervenor decided. The effect metric must use posted messages, not dispositions alone.
- Pinned `failure_reason` values: `structural`, `budget_exceeded`, `budget_unavailable`, `refused`, `breaker_open`, `llm_disabled`, `model_not_allowed`, `api_error`, `internal_error`, `invalid_trigger`.
- `config_snapshot` keys: `models`, `max_tokens`, `prompts` (the fingerprint), `tunables` (`TRANSCRIPT_MAX_MESSAGES`, `MAX_ACTS_PER_INTERVENTION`); written when the run is claimed, so failed and skipped runs have it too.
- The Intervenor sees the Master's `local_id`s, not database keys; dispositions and source ids are matched on `local_id`.
