## Two-position model (owner decisions 2026-09-26, final; it overrides every conflicting sentence above)
**Rules.**
- Every proposition has two positions. **`pro`** = the stated position: `Topic.proposition`, shown as "My position is that <proposition>". **`con`** = the opposing position: `Topic.opposing_position` when set (seeded topics carry both wordings), otherwise the plain choice "I disagree with this position".
- A person **chooses a side** when entering a proposition. Each participant records a `side` (`pro` or `con`); the two participants of a conversation always hold opposite sides.
- **Pairing** (`enter_proposition(user, topic, side)`): (1) the user's own open or active human conversation on the topic is returned (unchanged, whatever its sides); (2) `too_many_open` check (unchanged); (3) otherwise the oldest `open` human conversation on the topic with exactly one participant, who is not the user, **whose participant holds the OPPOSITE side**, is joined (labels: the joiner gets the label the creator did not; the joiner's side is the chosen one; the conversation becomes active); (4) otherwise a new waiting conversation is created and the user is its only participant with the chosen side (the label is drawn at random at creation with the seed stored at creation, see the 7c back-end task 1). Two people waiting on the same side do not pair. A legacy waiting conversation whose only participant has a blank side counts as `pro`.
- The AI moderator and the raters are unchanged: they get only the neutral claim (`Topic.proposition`), never sides, labels or roles.
- User-created propositions: the proposer writes only their own position; the form shows the fixed start "My position is that" and the proposer completes it; they enter with side `pro` in the same atomic action as before. `Topic.opposing_position` stays blank for them.

**Database (forum migration 0003, the 7a builder owns models and migration).**
- `Topic.opposing_position`: `TextField(blank=True, default="")`.
- `Participant.side`: `CharField(max_length=3, blank=True, default="", choices=[("pro","pro"),("con","con")])`.
- A conditional `UniqueConstraint(fields=["conversation","side"], condition=~Q(side=""), name="forum_participant_side_unique_per_conversation")`, and a `CheckConstraint` that `side` is one of `""`, `pro`, `con`. Existing rows keep `side = ""`. The migration must reverse cleanly; generate it in a scratch copy of the repo and move it in; do not run migrate against `db.sqlite3` (the architect migrates the dev database).
- Model validation: `Participant.save()` refuses any other side value; nothing else in the models changes. Synthetic (replay) participants keep a blank side.

**Back end (adds to the 7c-back tasks).**
- `create_proposition` stores the typed text as the claim with its first letter upper-cased; if the text already begins with "My position is that" (any case) strip it; the stored proposition never contains that start; the 200-character limit applies to the stored claim.
- `enter_proposition(user, topic, side)`: `side` is required and must be `pro` or `con` (else `PostRejected("invalid_side", "Choose a position first.")`); behaviour as in Rules. `propose` in the views enters with `pro`.
- `waiting_previews(topics, viewer)` (see above) now returns per topic: `{"side": "pro"|"con", "text": ..., "shortened": bool}` where `side` is the side the WAITING person holds (a legacy blank side counts as `pro`), so the page can attach the preview to the button that would join them. The viewer's own conversation on a topic suppresses the preview as before.
- `conversation_view` for the viewer adds `"my_side"`, `"other_side"` (`"pro"|"con"`, other is None while waiting), `"position_texts"`: `{"pro": <proposition>, "con": <opposing_position or None>}`. Nothing else about the other participant.
- `seed_topics` (the 7a builder owns `forum/management/commands/seed_topics.py` and `forum/seed_topics.json` for this task): the seed file gains an `opposing_position` string per entry (required for the six seeded entries; the command validates it non-empty, at most `MAX_PROPOSITION_CHARS`, different from the proposition) and stores it; idempotent update includes it. They are drafts for the owner's review. The `leans` structure is unchanged (`pro` = holds the proposition).

## Revision 5 (owner decisions 2026-09-26): usernames are shown, and people can block each other
**Schema (forum migration 0004, the 7a builder owns models and migration; generate it in a scratch copy of the repo; do not run migrate against `db.sqlite3`).** New model `forum.Block`: `blocker` FK `settings.AUTH_USER_MODEL` (PROTECT, related_name `blocks_made`), `blocked` FK (PROTECT, related_name `blocks_received`), `created_at`; `UniqueConstraint(blocker, blocked)`; `CheckConstraint(~Q(blocker=F("blocked")))`. No other schema change.

**Back end (7a builder), `forum/services.py`:**
- `block_user(blocker, target)`: refuses anonymous, self and unknown users (`PostRejected` with codes `login_required`, `invalid_block`); idempotent; in one transaction it creates the `Block` (if missing) and ends every `open` or `active` human conversation the two share, exactly as `end_conversation` does (`ended_by` = the blocker's participant, closed for both, read-only). Returns the list of ended conversation ids.
- `unblock_user(blocker, target)`: removes the `Block` (idempotent); it does not reopen anything.
- `blocked_users(viewer)`: the users the viewer has blocked (`[{"username", "since"}]`, newest first). `is_blocked_between(a, b)`: True if either blocked the other.
- **Everywhere a viewer looks at or joins someone else, blocks apply in BOTH directions:** `waiting_groups(viewer, ...)` skips a group whose oldest joinable waiting conversation belongs to a person the viewer blocked or who blocked the viewer, and shows the next joinable one of that group if there is one (so a group appears only if a non-blocked waiter exists); `enter_proposition` never joins a waiting conversation whose only participant is blocked in either direction with the joiner (it falls through to the next oldest allowed waiter, else creates a new waiting conversation); a blocked person's existing conversation with the viewer stays in "Your discussions" (ended, read-only). `my_conversations` rows gain `"other_username"` (the other participant's username, or None while waiting). `conversation_view` gains `"other_username"` for the viewer (None while waiting) and, for each message, `author_name` (`None` for the viewer's own and for moderator messages, the other participant's username for theirs); moderator headings that used "the other participant's message N" now use `"<username>'s message N"` (still "your message N" for the viewer's own, "For both of you", "About the conversation").
- `waiting_groups` entries gain `"waiting_username"` (the waiting person's username).
- Nothing about usernames, blocks or sides may reach the moderation code, the prompts or `LLMCall` requests (the existing privacy tests stay, adapted only where they forbade usernames on the participant pages).
- Add read-only admin for `Block` (list: blocker, blocked, created; no add, change or delete) in `forum/admin.py`.
