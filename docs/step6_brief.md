## 6a. Registration, email confirmation, resend
URLs (all in `registration.urlpatterns`): `register/` (name `register`), `register/check-email/` (`check_email`), `confirm/<token>/` (`confirm`), `resend-confirmation/` (`resend`).
- **Register:** form with username, email, password and password confirmation (server-side validated with the model's username validator, `validate_password` from settings, matching passwords, a well-formed email). On success create the user with `is_active=False`, send the confirmation email, redirect to `check_email` (a page that says: "We sent a confirmation link to that address. It expires in 3 days. Check your spam folder." and links to resend). Username problems are shown on the form (friendly messages from the model: taken, wrong characters, length). **Email enumeration is avoided:** registering with an email that already belongs to a confirmed account, or to a pending one, looks identical to a fresh registration on the page ("check your email"); for an existing confirmed account the email sent says an account already exists for this address and links to login and password reset, and no second account is created; for a pending unconfirmed account, a fresh confirmation link is sent (subject to the resend limit).
- **Token:** signed and expiring (`django.core.signing`, purpose-specific salt), carrying the user id and a value that changes when the account is activated so the link works **exactly once**; max age `EMAIL_CONFIRM_MAX_AGE_DAYS` days. Tampered, expired, or already-used links give a clear page: expired ("This link has expired. Request a new one.") with a resend form; already used ("Your email is already confirmed. You can log in."); invalid ("This link is not valid.").
- **Confirm:** activates the user (`is_active=True`, `email_verified_at=now`), shows "Your email is confirmed. You can now log in" with a login link. Never logs the user in automatically.
- **Resend:** form asking for the email; always answers "If that address has an unconfirmed account, we sent a new link" (no enumeration); rate limited per address by `RESEND_CONFIRMATION_MIN_SECONDS` (store the last send time on the user in a new nullable field `confirmation_sent_at`, migration `accounts/0003`, or use the cache; the builder decides and tests pin it); when rate limited the page says "Please wait N seconds before requesting another link" (this reveals nothing beyond a rate limit that applies to every address, so apply it to ALL submitted addresses, existing or not, keyed by the address, so the message is the same either way).
- **Email:** plain text, subject "Confirm your email for the discussion forum", body with the absolute link (built from the request's host with `request.build_absolute_uri`), the expiry in days, and a line saying to ignore it if not requested. Sent through the default MAILERS mailer. Sending failures must not create a half-registered state that cannot recover: the user is created, the page still says check your email, the error is logged (no address or token in the log), and resend works.
- Security: CSRF on every form; passwords never stored or logged in plaintext; no token in logs; every user-visible string free of internal details; new accounts cannot log in until confirmed (enforced by 6b's login via `is_active`).

## 6b. Login, logout, throttling, password reset and change
URLs (all in `authviews.urlpatterns`): `login/` (`login`), `logout/` (`logout`, POST only), `password-reset/` (`password_reset`), `password-reset/sent/` (`password_reset_done`), `reset/<uidb64>/<token>/` (`password_reset_confirm`), `reset/complete/` (`password_reset_complete`), `password-change/` (`password_change`), `password-change/done/` (`password_change_done`).
- **django-axes (8.3.1):** add `"axes"` to `INSTALLED_APPS`, `axes.middleware.AxesMiddleware` (last), the axes backend first in `AUTHENTICATION_BACKENDS` with `django.contrib.auth.backends.ModelBackend` second. Read the installed package's documentation and source to configure the current 8.x settings correctly: lock after `LOGIN_MAX_FAILURES` failures, cool-off `LOGIN_COOLOFF_MINUTES` minutes, throttling by username AND by IP (either can lock), reset on successful login. Do not hard-code numbers; use the tunables.
- **Login:** username and password. A wrong username or password gives one generic message ("Incorrect username or password."). **Correct credentials on an unconfirmed account** (inactive) show "Please confirm your email first; we sent you a link when you registered" with a link to `accounts:resend` (safe: only someone who knows the password sees it). A locked-out user sees "Too many failed attempts. Try again in N minutes." (say why and when; the message must not reveal whether the username exists beyond what the lockout itself implies). `?next=` is honoured only for same-host URLs. Successful login redirects to `LOGIN_REDIRECT_URL` (or safe `next`).
- **Logout:** POST only, CSRF protected, redirects to `LOGOUT_REDIRECT_URL` with a confirmation message.
- **Password reset:** Django's flow with our templates, plain-text email through MAILERS, token lifetime the Django default; the "sent" page always says "If an account exists for that address, we sent instructions" (no enumeration); inactive (unconfirmed) users get the reset email too or not, the builder decides and documents; the new password goes through `validate_password`; after a reset all sessions of that user are invalidated (Django's behaviour; verify); reset link works once.
- **Password change:** login required; old password required; validators applied; the session stays logged in (`update_session_auth_hash`); confirmation page. 
- Security: CSRF, generic errors, no timing-obvious differences beyond Django's defaults, cookies as configured, `POST` for state changes.

## Amendments (architect, after the 6a/6b builders' reports)
- Resend limit lives in the cache keyed by a hash of the normalised address (so unknown and known addresses behave identically); a shared cache backend is a deployment-step item (plan note).
- Every registration/confirmation/resend response is HTTP 200; confirm uses `confirm/<path:token>/` so mangled links get the invalid page.
- Lockout responds with HTTP 429 and "Too many failed attempts. Try again in N minutes."; attempts during a lockout do not extend it; client IP is `REMOTE_ADDR` only (reverse-proxy settings are a deployment item).
- Unconfirmed accounts do not receive password-reset emails; the "sent" page points them to resend.
- Correct credentials on an unconfirmed account count as one failed attempt toward the lock (accepted).
- The home page does not yet render Django messages, so the logout message is invisible until step 7's base template shows messages (step 7 must include a messages block).
