## Behaviour
- **Without JavaScript nothing changes**: the composer is an ordinary form posting to `c/<id>/post/`; no check happens. With JavaScript, pressing "Post message" first checks the draft.
- **The conversation page carries `data-preview="on"` or `"off"` on the composer form** (from `moderation.preview.preview_mode(conversation_id)`, called only for a participant of an open or active conversation; never for a closed one). `off`: no interception at all.
- **`on`, JS enabled:** submit is intercepted. The button becomes disabled with the label **"Checking your message…"** and a polite live region (`aria-live="polite"`) says the same. The script POSTs the draft (with the CSRF token) to `c/<id>/check/` and waits up to `PREVIEW_CLIENT_TIMEOUT_SECONDS` (new tunable, default 25, exposed as `data-check-timeout` in milliseconds or seconds, your choice, documented). Result handling:
  - `no_concern`, `unavailable`, a timeout, a network error or any unexpected reply: the script submits the original form for real (a normal post), with a hidden `check_id` field added when the reply carried one. The person sees nothing extra. (Never block posting because the check failed.)
  - `refused` (the draft breaks a posting rule: too long, too fast, empty, closed, not a participant): the script shows the same refusal message inside the existing alert area, keeps the text, re-enables the button, and posts nothing. The wording is the server's (`PostRejected.message`).
  - `concern`: a panel appears under the composer (role `region`, focus moved to its heading): heading **"The moderator would reply to this message"**; text **"If you post it as written, the AI moderator will reply:"**; then the note texts in quote blocks (escaped plain text, one block per note, never bold, `white-space: pre-wrap`); then two buttons, **"Edit my message"** and **"Post as written"**. "Post as written" submits the original form with the hidden `check_id`. "Edit my message" hides the panel, returns focus to the text box with the text kept, re-enables the button, and sends `POST c/<id>/check/<check_id>/edit/` in the background (its failure is ignored). Pressing Post again on the same unchanged text calls the check again (a new check).
- **Endpoints (forum/views.py, forum/urls.py):**
  - `POST c/<id>/check/` (login required, CSRF, participant only, else the standard not-found page): form field `text` (same name as the post form). It validates the draft with the SAME rules and messages as a post, WITHOUT creating anything (`services.validate_draft(user, conversation, text)`: the checks of `post_message` factored out, in the same order: not a participant, closed, empty, too long, too fast, conversation full; the back end refactors `post_message` to use it, behaviour unchanged). On `PostRejected`: `{"status": "refused", "code": ..., "message": ..., "retry_after": ...}`. Otherwise it calls `moderation.preview.check_draft(...)` (wrapped: any exception gives `{"status": "unavailable"}`) and returns `{"status": "no_concern" | "concern" | "unavailable", "check_id": <id or null>, "notes": [<note texts>]}` (notes only for `concern`). Always `Cache-Control: no-store`, JSON content type, status 200 except CSRF/login/404/405 as elsewhere. Nothing else about the check (outputs, mode, reasons) is ever returned.
  - `POST c/<id>/check/<check_id>/edit/`: participant of that conversation and owner of that check only (else 404): `resolve_check(check_id, "edited")`; returns `{"ok": true}`.
  - `POST c/<id>/post/` accepts an optional `check_id`. After a successful post, if the check belongs to the poster's participant in this conversation and its `draft_sha256` equals the message's, call `resolve_check(check_id, "posted_as_written", message_id=<new message id>)`; otherwise ignore the field silently. It must never change whether the post succeeds. (Reuse of the model outputs by the live run happens automatically in the pipeline; do not touch it.)
- **Privacy:** the draft and the check are visible only to the author; nothing about them appears in polling JSON, exports, logs or another participant's page. No username, label, side or mode is sent anywhere new.
- **Failure of the back end** (`preview_mode` raising, for example): the composer renders with `data-preview="off"`.
- **Accessibility:** buttons are real buttons with 44px targets, the panel is reachable by keyboard, focus moves into the panel and back, the live region announces "Checking your message…" and, on concern, "The moderator would reply to this message."
- **No new user-facing cost wording; no "debate".**
